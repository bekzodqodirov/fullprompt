# Review of the two specs before code (2026-10-06)

`docs/VED-TARIX.md` and `docs/TELEGRAM-TOPSHIRIQ.md` were judged against the
code by five lenses (VED correctness; access and money; Telegram mechanics;
data and migration; tests and completeness), each objection then given to a
skeptic who tried to refute it. **115 objections: 88 confirmed, 25 partial,
2 refuted.** Every surviving one is listed below with the fix the skeptic
settled on. They are BINDING on the build: where a fix below and the spec
text disagree, the fix wins. The owner's decisions are not re-opened here —
two questions this review raised went back to him (VED-TARIX §13).


## VED-TARIX (64)

- **ved-correctness-1** · defect · §6 «Qayta hisoblash on an answered job» — assignment
  - «Assigned to the person who priced the parent when they can still sign in and hold ved.docs» routes corrections to the OWNER. That brings back the defect audit A13 fixed after his «1.1»: the rota leaves out super_admin/admin because they hold ved.docs.
  - **Fix:** §6: prefer the parent's pricer only if canLogIn, holds ved.docs and is NOT in usersWithRoles(['super_admin','admin']). That is the same subtraction as nextVedAssignee; extract it as one predicate both functions call. Otherwise use nextVedAssignee(), and leave the job unassigned (no task) when that is null. The admin keeps «Olaman».
- **ved-correctness-2** · defect · §6 seller sentence «eski narx endi amal qilmaydi» + §2 dealCalcSheets rule
  - The new Telegram sentence matches the money rules but contradicts three existing display surfaces that §2/§6 leave as they are. Widening recalc to answer parents creates states those surfaces already describe wrongly.
  - **Fix:** §6: add a display table for the three new answer-parent states (open / answered / returned child) on the sheet's answers, the card's «Javob berildi» line and the answer door. Use the same words as the chain chip (see -15/-16). Re-text calcRecalcOpen ×4 so it no longer says «eski narx turibdi» (e.g. «qayta hisoblanmoqda»). The sheet may keep its display rule, but its words must not contradict the seller's push. Add an integration test: answer → recalc → sheet, panel and registry all mark A as not standing.
- **ved-correctness-3** · defect · §7 Nazorat READ scope = all for ved.docs

  - **Fix:** §7: the queue is two lists from one predicate.
- «Meniki» (write scope): buttons, and the count the home shows.
- «Hamkasblar» (read scope minus own): read-only rows, no CalcLinkRow, and the sealer's name.

Print both counts, so the home number is one the screen prints. Edit calc-control-scope.test.ts and add a test that a colleague's row has no link-confirm.
- **ved-correctness-4** · defect · §6 «The card panel stops letting «any seal» outrank the answer»
  - The card's quote LOCK still follows «any seal». So in exactly the chain shapes this round creates, the lock holds a dead seal's floor while the card shows a different number, and every ✏️ save on the card is refused.
  - **Fix:** §6: one sentence. quoteLockedFor follows the same standing list as the panel (see -6): lock to the newest NOT-superseded current seal, or to a standing released offer, and return null when nothing on the card stands. Add an integration test: released offer on V1 → recalc → a lead ✏️ save re-posting the shown quote is accepted.
- **ved-correctness-5** · defect · §6 refusals + §6 recalc_open chips (returned child)
  - A correction that is handed back leaves a chain that can never be corrected again, and the words point the person at a door that refuses them. Widening recalc to answers makes this path more common: a re-pricing that cannot be priced is exactly what gets handed back.
  - **Fix:** §6: add a refusal `recalc_returned` ×4, «Tuzatish qaytarilgan — kartadan yangi hisoblatish yuboring» (the only door is a new root request). The chain chip and the sheet say «tuzatish qaytarildi», and the card panel says nothing stands. Add a test: answer → recalc → return → recalc on the parent asserts recalc_returned.
- **ved-correctness-6** · defect · §6 panel «whichever price STANDS by the chain's edge»
  - The rule cannot be computed from the existing helpers, and it has no tie rule. A deal carries several jobs (0085), so a standing seal and a standing answer can live on one card. The helpers return only the NEWEST seal and the NEWEST answer, not the standing ones.
  - **Fix:** §6: define `standingAnchorsFor(entity)` (current, not-superseded seals plus answers passing answerFloorStandsSql) and draw one door per standing anchor, labelled with its section. Alternatively state a precedence. Say explicitly whether an expired-but-standing seal still hides an answer. The panel, quoteLockedFor (-4) and the card's «Javob berildi» line read this one list.
- **ved-correctness-7** · defect · §4/§6 «an answer is never V-ranked», «the old one stays in history»
  - The chain view only knows SEALED versions, so an answer link vanishes from every chain surface except the registry. On a seal corrected by an answer, or an answer corrected by a seal, the workspace, the card's «Oldingi» line and the sheet's `previous` say nothing about the other link.
  - **Fix:** §6: the closed request page (answered or sealed) prints its chain from one reader that returns both kinds, in price-moment order: seals with V numbers, answers as «✍️ umumiy narx amount currency». The V-rank stays seal-only. The card's «Oldingi» line and the sheet's `previous` may stay seal-only, but say so.

  - The existing hook runs AFTER the task is already marked done, inside a catch that swallows every error so the close can never be stopped. Built «through the existing hook», the refusal comes too late and is swallowed: the task is done, and the request stays open with nobody's task.
