# DECISIONS.md

> Running log of ambiguity resolutions, per SPEC.md §0: "If a requirement is ambiguous, choose the simplest interpretation that satisfies the acceptance tests, note the decision in DECISIONS.md, and continue." Newest entries are appended at the bottom.

## Pre-implementation decisions (planning stage)

Each item: the ambiguity → **DECISION** (simplest interpretation) → why it satisfies the acceptance tests (Section 20) and edge cases (Section 14).

1. **Monorepo vs single app packaging.** Spec says "single monorepo, modular folder structure" but also "Next.js — single full-stack app."
   **DECISION:** One pnpm workspace containing one deployable Next.js app; "modules" are internal source folders/packages (`modules/platform`, `modules/wms`) with enforced import boundaries (ESLint rule), not separate services or separate deployments.
   **Why:** No acceptance test requires independent deployment; single app keeps Docker Compose simple and meets the 3G performance budget; boundaries still make CRM/Finance cheap to add later.

2. **Primary keys: UUID vs serial.** Spec never says.
   **DECISION:** UUIDv7 for all PKs; business codes (`GS777`, `YW26-000123`, `YW-001`) are separate unique columns, never PKs. Sequence counters (letters, box seq, batch seq) live in dedicated counter columns/tables updated under row locks.
   **Why:** Edge case 16 requires "codes are labels, FKs are ids"; offline sync already mandates client-generated UUIDs (test 18), so UUIDs unify online/offline creation; UUIDv7 keeps index locality at the 200k-box scale.

3. **`planned` reservation when plan lines are lot-level but boxes are the unit.** Which 50 of 100 boxes get reserved?
   **DECISION:** Reservation is a *count per lot per approved plan* (`available = box_count − Σ reserved counts`). For visibility, the N lowest `seq_in_lot` boxes in `in_stock` are stamped `planned`, but boxes of a lot are **interchangeable at scan time**: scanning any in-stock sibling box counts against the line (reservation swaps to the scanned box). Over-scanning beyond the planned count triggers the `added_on_spot` path.
   **Why:** Test 10 only requires that 50 depart and 50 remain `in_stock`, and that double-planning is prevented — a count-level guard does both. Pinning specific physical boxes would cause false "not on plan" alerts, contradicting test 11's intent and warehouse reality (identical boxes).

4. **Crated boxes' statuses vs crate status.** Do member boxes keep their own status while `crated`?
   **DECISION:** Boxes keep `crate_id` and continue through the normal status machine; `crated` is a location attribute, not a terminal state. A crate scan fans out to all member boxes (one scan_event per box, `method=crate`), and the crate's status/location is derived from its members (they always move together while the crate exists). Crate codes get their own per-WH-per-year sequence (`CR-{WH}{YY}-{00000}`).
   **Why:** Test 19 ("scanning crate at load counts all 18") and 5.5 ("scanning the crate QR = scanning all boxes") work naturally; per-box landed cost (test 16) requires per-box batch membership, which fan-out preserves.

5. **Receipt edit after boxes already loaded/in transit.** 4.4 allows manager edits "after that" with no downstream guard.
   **DECISION:** Structural fields (box_count, dims mode, per-box dims/weight) are locked once any box of the lot has left `in_stock` at the origin WH; only text/photo/attachment fields stay editable (audited). Fixing structural errors after departure goes through the void/deviation paths, not receipt edit.
   **Why:** Prevents retroactive corruption of manifests and cost denominators that tests 13 and 16 depend on; label reconciliation (4.4) only makes sense while boxes are still at origin.

6. **Per-box weight when the lot is `mixed` (boxes have no individual weight) but allocation basis is weight.**
   **DECISION:** A box's kg (and m³) = lot total ÷ box_count — the uniform average — used for allocation, manifests, and capacity gauges. If the optional per-box list was entered, real per-box values win. Chargeable weight of a box derives from these same values.
   **Why:** Test 16's worked example uses per-box kg; averaging makes every box well-defined with zero extra operator input (edge case 8: "can't measure each"), and sums remain exactly the lot totals, so batch denominators stay correct.

7. **`direct_to_client` allocation basis semantics.**
   **DECISION:** The cost entry carries a required `client_id`; the amount is distributed only over that client's boxes within the entry's scope (receipt or batch), proportionally by weight. If the client has no boxes in scope, the entry is rejected at save time.
   **Why:** Keeps the invariant "box landed cost = Σ shares" (6.9) — Finance later needs everything at box level; weight is the spec's stated default basis, so no new concept is introduced.

8. **Letter preview race.** Wizard shows "≈ D, E, F" but another operator may confirm first.
   **DECISION:** Preview is a non-binding estimate (already marked "≈"); no letters are reserved at draft time; actual assignment happens only inside the confirm transaction with the warehouse row locked. If assigned letters differ from the preview, the confirm result screen simply shows the real ones.
   **Why:** Test 4 (concurrent confirms get disjoint letters) is satisfied by the transactional assignment alone; reserving at draft time would leak/park letters and violate 5.3's immutability rule.

9. **Batch code for quick batches (AND→TAS, TAS1→TAS2).**
   **DECISION:** Same per-origin-WH sequence and format as any batch (e.g., `AND-003`, `TAS1-007`). A quick batch auto-creates a load plan with a single auto-`approved` version (no agent loop), so loading mode, manifest, deviations, and costing reuse the same code path.
   **Why:** 6.8 says internal moves are "normal transfer batches"; one uniform pipeline means tests 10–14 and the allocation engine (16) apply unchanged to UZ-side moves.

10. **Timezone for the "same warehouse-day" edit rule.**
    **DECISION:** The creator's free-edit window ends at midnight in the *receipt's warehouse* timezone, comparing the warehouse-local calendar date of `created_at` to the warehouse-local date of "now." (Not the editor's locale, not UTC, not a rolling 24 h.)
    **Why:** Section 3 already mandates WH-local display/print time; this matches the operator's shift reality and is deterministic for the audit trail (test 17).

11. **Session storage.**
    **DECISION:** Opaque session IDs in a Postgres `sessions` table (user, device label, UA, IP, created/last-seen, revoked), referenced by the httpOnly cookie. No Redis, no JWT for normal auth.
    **Why:** 4.1 requires a device list and "logout other devices," which needs server-side session state; spec explicitly avoids Redis; JWT stays reserved for the print helper only.

12. **What `received` vs `in_stock` mean practically.**
    **DECISION:** `received` is not a stored box status — the `boxes` status set starts at `in_stock`: receipt confirmation creates boxes directly as `in_stock`, and the single confirm movement row in `box_movements` represents spec 5.5's `received → in_stock` arrow. Operationally, a confirmed box is immediately available for planning/crating. (Aligned with the schema in ARCHITECTURE.md — one source of truth.)
    **Why:** No test or workflow ever acts on a lingering `received` state; keeping the arrow in the movement history honors 5.5 without inventing an extra manual step for the operator (3-minute budget, 6.1).

13. **Label reprint for unclaimed → assigned cargo.**
    **DECISION:** Box short codes (QR payloads) never change on assignment. The assign-to-client flow ends with a "Reprint N labels" button generating labels with the new client code + existing letters; old `#UNKNOWN` labels are flagged "to be replaced/destroyed" in the same reconciliation UI as 4.4; physically re-stickering is the operator's manual act. Unclaimed lots receive letters normally at confirm (label shows `#UNKNOWN` + receipt number in the client-code slot).
    **Why:** Test 9 requires "labels reprintable with new code" with both actors audited; stable QR payloads mean already-applied stickers still scan correctly even if not replaced.

14. **FX rate selection "on the cost date."**
    **DECISION:** Use the latest rate whose date ≤ the cost entry's date for the (currency → USD) pair; if none exists, saving the entry prompts the user to enter today's rate first (no silent fallback). Rate edits trigger the idempotent recompute job.
    **Why:** Test 16 needs "each entry's dated rate" to be deterministic; edge cases 17–18 (late costs, corrected rates) are covered by the recompute path.

15. **Cost allocation denominator and membership changes.**
    **DECISION:** A batch entry's denominator = Σ (basis metric) of boxes *actually on the batch* per the reconciled manifest (including `added_on_spot`, excluding `short_loaded`). Any later membership change (late scan, missing-in-transit resolved, undocumented transfer) re-triggers the recompute job for affected batches.
    **Why:** This is the only reading under which test 16's arithmetic (10,000 CNY / 10,000 kg actually loaded) and test 13/14 resolutions stay mutually consistent.

16. **`ready_for_pickup` at AND when cargo continues to Tashkent.** Section 1 says pickup happens "after customs clearance"; 6.8 says boxes become `ready_for_pickup` right after unload at any customs/distribution WH.
    **DECISION:** Follow 6.8 literally: unload at a `customs`/`distribution` WH sets `ready_for_pickup` for all clients' boxes. Planning boxes into an onward quick batch transitions them `ready_for_pickup → planned/loading` (allowed extra arrow). Customs clearance itself is not modeled in Phase 1.
    **Why:** 6.8 is the operative workflow section; test 20 (partial pickup) and the notification rules (Section 11) key off `ready_for_pickup` at unload; modeling clearance would add a state no test exercises.

17. **Density badge boundaries.** "🟠 300–400, 🟢 200–300" leaves ties ambiguous.
    **DECISION:** Lower-bound inclusive intervals: blue < 200, green [200, 300), orange [300, 400), red ≥ 400.
    **Why:** Test 5 fixes the only tested tie: density exactly 200 → 🟢.

18. **Receipt-number and box-code sequence scopes.**
    **DECISION:** Receipt seq resets per WH per warehouse-local day (matching the date in the number). Box short-code sequence is per WH per year (`YY` in the code), rolling over at WH-local Jan 1; batch seq per origin WH, never resets. All counters use `SELECT … FOR UPDATE` like the letter sequencer.
    **Why:** Mirrors the formats in 5.2 exactly; the concurrency guarantee of test 4 is reused for every counter for free.

19. **Loading a crate whose member lots are only partially on the plan.**
    **DECISION:** Crate scan evaluates each member box against the plan individually: members whose lot line still has remaining planned count are counted; members beyond plan go through one aggregated `added_on_spot` confirmation (single reason for the whole crate).
    **Why:** Keeps test 11 and test 19 simultaneously true without forcing the logist to pre-model crates in plans.

20. **Offline receipt-draft identity.**
    **DECISION:** Drafts and scan events both carry client-generated UUIDs used as idempotency keys on sync; a draft syncs as `draft` status and is only ever *confirmed* online (letter assignment requires the DB transaction). Offline confirm is not supported — the wizard queues the draft and prompts to confirm when back online.
    **Why:** Test 18 requires dedupe; 5.3 makes letter assignment inherently online-transactional, and 6.1 only requires drafts to survive connection loss, not offline confirmation.



## Completeness-review addendum (pre-implementation)

A cross-check of the draft plan against every spec section surfaced these additional resolutions:

21. **Seed timing vs spec §18 ("must ship with M1").** The batch seed (`YW-001` departed, `KA-001` in approval loop) and cost/FX seed require M3/M6 schema. **DECISION:** the seed script grows with each milestone — warehouses/users/clients at M0, the canonical receipts at M1, batches + presets at M3, cost entries + FX at M6 — so each §18 item ships with the first milestone whose schema supports it.

22. **Batch status set.** Spec §6.5 uses `unloaded`/`closed`, the kanban (§10) uses Arrived/Closed. **DECISION:** statuses are `forming, loading, in_transit, arrived, unloaded, closed, cancelled`; `arrived` = truck at destination, `unloaded` = finish-unload reconciliation done; the kanban "Arrived" column shows both `arrived` and `unloaded`.

23. **Currencies are a table, not a hardcoded list.** `currencies` (`CNY`,`USD`,`UZS` seeded, admin-extensible per §4.6); cost-entry UI defaults to CNY at `country='CN'` warehouses (§6.1).

24. **Offline scanning scope.** The IndexedDB outbox built in M3 for Loading mode is a shared primitive reused verbatim by Unload (M4) and Issue (M5) modes — §15's "all scan modes fully functional offline" is satisfied by reuse, not per-mode reimplementation.

## M0 implementation decisions

25. **Translation provider (owner's answer, 2026-07-22).** Owner chose a free/open translation API for now, to be swapped for a paid provider later. **DECISION:** `translation_provider` defaults to `libretranslate` (self-hostable/open); the provider interface stays pluggable per spec §8, so switching to Yandex/DeepL is a settings + API-key change. Wired up in M1 with the product dictionary.
26. **Telegram bot token** provided by the owner; stored only in `.env` (gitignored) as `TELEGRAM_BOT_TOKEN`, never committed. Bot integration itself lands in M1 per the plan.
27. **UI fonts = system font stack** (no webfont files at all): zero font bytes on 3G, inherently China-safe, and CJK renders via the OS. Label PDFs will embed a self-hosted CJK font separately in M1 (pdf-lib needs a real font file).
28. **Local-disk storage driver for dev** behind the same `StorageDriver` interface as S3/MinIO, with HMAC-signed serve URLs so the signed-URL access model (spec 4.8) holds in dev too. `STORAGE_DRIVER=s3` in production compose.
29. **Audit immutability enforced twice**: `REVOKE UPDATE/DELETE` (covers the non-superuser app role in production) **plus** a `BEFORE UPDATE OR DELETE` trigger raising an exception — the trigger also protects dev databases where the app connects as a superuser.
30. **pg-boss runs in-process** with the Next.js server, started from the `instrumentation` hook — matches the single-app Docker topology (spec §3); a separate worker container can be split out later without code changes.
31. **Password hashing via `@node-rs/argon2`** (prebuilt native binding) with OWASP Argon2id parameters — the `argon2` npm package needs node-gyp toolchains that complicate CI/Docker.
32. **`settings` audit rows** use the fixed entity id `00000000-0000-0000-0000-000000000001` (audit_log.entity_id is `uuid NOT NULL`; settings keys are strings — the key lives in the diff payload).

## M1 implementation decisions

33. **Client-generated receipt/lot UUIDs.** The wizard mints receipt and lot ids client-side: photos upload against the lot id *before* confirm (no orphan-attachment repointing), and the receipt id doubles as the idempotency key — a double-tap or offline retry returns the already-confirmed receipt instead of duplicating it.
34. **Draft autosave = localStorage (M1).** Wizard text state persists to localStorage after every change and survives app kill; photos upload immediately when online. The full IndexedDB outbox (photos offline, scan events) arrives with the M3 scanner per the plan — recorded as the M1 slice of spec §15 offline.
35. **Letter preview is non-binding** (spec DECISIONS #8 confirmed in code): shown as "≈ D, E, F"; real assignment only inside the confirm transaction.
36. **Seed letters mirror the owner's canonical example**: fixed UUIDv7-format ids make the M1 seed idempotent; GS777 → A/B/C and GS102 → D are created through the real `confirmReceipt` service, so seed data exercises the production code path.
37. **Label CJK font**: Noto Sans SC subset-embedded via pdf-lib+fontkit (~50 KB per PDF). Verified with pdf.js (the Chrome/Android renderer family); poppler warns on the CFF subset but that does not affect RawBT/browser printing. Latin text uses built-in Helvetica (codes stay crisp at 203 dpi).
38. **Telegram delivery model**: notification rows are per-(user, channel); the in-app bell row is written immediately, the Telegram row is sent by a pg-boss worker with retry/backoff — delivery failures stay visible on the row (admin view arrives in M6 polish).

## M1.6 decisions (owner feedback round 2, 2026-07-23)

44. **"Pieces" (sht) field replaced with a free-text note per line.** The owner's real Kashgar file concatenates a remark into the product-name cell (e.g. "loader miscounted during loading"); modeling that as a dedicated `note` column is more faithful and more useful than a numeric pieces count nobody asked to keep. `pieces_count`/`packaging_type` columns were dropped (not deprecated) since no production data existed yet.
45. **Receipt-level attachments are a separate concept from per-lot box photos.** Per-lot photos (`entityType='receipt_lot'`) remain the mandatory "box appearance" proof required to confirm; receipt-level attachments (`entityType='receipt'`) are optional supporting documents (invoice, packing list, anything) shared across the whole receipt. Reused the generic `attachments` table and upload API — only the entityId differs.
46. **Responsive strategy: two renderings, one state.** Rather than one layout awkwardly serving both device classes, the product-line editor renders twice — a real `<table>` on desktop (`hidden md:block`) and the original stacked cards on mobile (`md:hidden`) — sharing the same `draft` state and update functions. Both are always in the DOM; CSS `display` toggles which one is visible. This is why e2e locators must scope to the visible container (`#mobile-product-lines`) rather than assume a single match.
47. **Desktop table keeps the mode toggle inline** rather than splitting into separate uniform/mixed table schemas — a single "dims" cell swaps its inputs, keeping column count stable and Excel-like.

## M3 decisions (2026-07-23, owner's answers)

63. **The agent never enters the system** (owner Q1): the logist downloads the plan Excel, sends it to the agent over Telegram/WhatsApp, and records the verdict (approved / changes_requested + comment) on the plan version. Versions are immutable; a resubmit after changes creates v(N+1).
64. **No server-side plan drafts**: the editor's working selection lives client-side; the first "send to agent" creates the plan directly in `pending_agent` (the schema's `draft` status stays reserved). Cheaper than draft persistence and matches how the logist actually works — build, send, done.
65. **Scan input = camera AND HID** (owner Q2): native `BarcodeDetector` when the browser has it, `@zxing/browser` fallback otherwise, plus a global keystroke listener for USB/Bluetooth HID scanners (they type the code + Enter). One `Scanner` component serves all future scan modes.
66. **Partial-lot plans don't pin boxes** (owner Q3): approval reserves the N lowest-`seq_in_lot` boxes as `planned`, but whichever boxes the loader actually scans are what departs — a scan of an unplanned box of the SAME batch-reserved lot still goes through the not-on-plan confirm, keeping the fact trail honest.
67. **Offline scans**: IndexedDB outbox with client-generated event UUIDs; `/api/scan/sync` acks per item and the server dedupes on the UUID (`ON CONFLICT DO NOTHING`); crate fan-out rows get `uuid5(boxId, eventUuid)` derived ids. The loading screen validates against a cached batch snapshot for <300 ms local feedback.
68. **SSE deferred**: the loading counter is local-first and the logist sees state on refresh; the `/api/sse` live-push layer (plan live-adds, remote progress) moves to the M4/M5 polish backlog — recorded as a deviation from the original M3 task list.
69. **Sticker-lost = manual entry from the unscanned list** (edge case 3): the loading screen lists the batch's unscanned boxes; tapping one (or typing its code) records a `manual` scan with reason `sticker_lost`. The reprint offer arrives with the M4 polish.
70. **Truck presets are seed-managed for now**: two real presets seeded (13.6 m / 90 m³ / 24 t and 17.5 m / 130 m³ / 28 t); a presets admin CRUD is deferred until the owner asks.

## M4 decisions (2026-07-23)

71. **Unload has no confirm dialog for off-manifest scans** (edge case 4, "reality wins"): a known box scanned at unload is ALWAYS accepted — on-manifest lands normally, off-manifest is auto-transferred to this warehouse with flag `undocumented_transfer`, a correcting movement, and an instant logist Telegram. The loader never decides; the system records reality and alerts.
72. **Unknown QR at unload links to the full receiving screen** rather than a separate mini-intake form — the receive screen is already single-window and fast; a second intake form would drift from it. The ack toast carries the link.
73. **First unload scan flips the batch to `arrived`** (no separate "truck arrived" button); `finishUnload` flags never-scanned manifest boxes `missing_in_transit` (they stay `in_transit` on the batch) and the resolutions are `found_at_origin` (back to origin stock) / `found_here` (into destination stock), manager-gated per #43.
74. **KA hub dashboard v1 = the /transit report**: in-transit/arrived batches + all missing-in-transit boxes in one screen; the fuller role dashboard with charts arrives in M6 as planned.
75. **Batch-scope cost entry UI deferred to M6** (with the FX/cost module) — the schema already accepts scope=batch entries on closed batches, so nothing blocks late cost capture when that UI lands.

## M5 decisions (2026-07-23)

76. **VED invoice/packing list are download-drafts, not in-app documents**: rows come from the actual manifest; the price column is blank with a live amount formula — the VED manager fills prices in Excel before sending (in-app price editing deferred until asked). The company header comes from settings keys `company_name/address/phone` — **owner still owes the real requisites (open Q4)**.
77. **`handovers` generalized** (migration 0009): `receipt_id` nullable + `client_id`/`debt_ok` added — one table for whole-receipt returns (M2) and client issues (M5), matching the original architecture sketch.
78. **Issue flow is one idempotent submit, not per-scan events**: the phone selects boxes locally (tap or scan against a local list — works offline until the final confirm), then a single `issueBoxes` call with a client-generated handoverId creates the handover, flips boxes to `issued`, writes `issue` scan_events, and notifies the sales manager with the remaining count.
79. **Client-notify "Share" = message drafts inside the manager's Telegram**: the ReadyForPickup notification carries ready-to-forward client texts in uz AND ru (owner's Q5 wording: arrived, being cleared) — no separate share UI.
80. **Quick batches are plan-less batches**: created directly from the batch board (manager gate `batches.depart_close`); the load scanner detects the absent plan and accepts any loose box at the origin (in_stock or ready_for_pickup) without the not-on-plan ceremony or flags.
81. **`ready_for_pickup` happens at customs/distribution unload** and those boxes stay issuable and quick-batch-loadable; plan approval marks batches to customs warehouses as `export`.
82. **Unclaimed labels print the box marking** (feedback round 5): the sticker's dominant text is `MARKING-A` (what is physically written on the cargo) with a small `#UNKNOWN` flag beneath — `#UNKNOWN` alone only when there is no marking. The renderer no longer overrides the code the route computed.
83. **A crate is one place in a plan** (migration 0011): `load_plan_lines.crate_id` — crated boxes leave loose availability, the editor offers whole crates as single ticks (place count = loose boxes + crates), and approval reserves the crate's exact boxes so loading the crate QR never trips not-on-plan.
84. **Truck presets are owner-managed** (`/trucks`, `plans.manage` gate): create/edit/hide with audit; the plan editor keeps a ⚙️ link next to the truck select. Hidden presets keep history but leave the dropdown.
85. **Vehicle info stays editable until the batch closes** — a wrong plate/driver is fixable after departure; the read-only card only appears on closed/cancelled batches.
86. **`fx_rates` is USD-base, per-currency, dated** (migration 0012): the M0 pair-based placeholder (from/to) was never written and got replaced wholesale. `rate_to_usd` = USD per 1 unit; lookup takes the latest rate ≤ the cost date (falls back to the earliest known); a currency with no rates leaves the entry unconverted and visibly flagged instead of guessing.
87. **Allocations are materialized** (`cost_allocations`, rebuilt whole per entry by an idempotent job): batch-scope shares distribute over the boxes that actually DEPARTED on the batch (current members before departure); recompute fires on entry create/void, FX edit (per currency) and batch depart. 128. **Drizzle renders a column unqualified in a single-table select — never interpolate `${table.column}` inside a correlated subquery** (found by the Phase 2.4 tests, and it had already bitten `warehouseFill` once): `db.select({...}).from(batches)` emits `select "id", "code" …`, so a `${batches.id}` written inside `(SELECT … FROM client_transactions ct WHERE ct.batch_id = ${batches.id})` reaches Postgres as a bare `"id"` and binds to the SUBQUERY's table. Queries with a join are unaffected (drizzle qualifies as soon as more than one table is in play), which is why the older report queries in `reports/queries.ts` were correct and this one was not. WHERE clauses are also unaffected — only the select list drops the qualification.

132. **CRM digests are per recipient and silent when empty**: today's follow-ups at 08:30 Tashkent (half an hour before the warehouse digest, so the two do not arrive as one wall of text) and the gone-quiet list on Monday 09:00. Each recipient gets THEIR OWN list — `crm.leads.view_all` decides whether that means everyone's — because a message about someone else's clients is a message people learn to swipe away. Both join the existing `digest` mute group: someone who muted the warehouse digest meant these too. The dormancy threshold is a setting (`crm_dormant_days`, default 60), and a client who never shipped is never listed — they are a lead with a card, and including them would bury the real signal.
133. **Kanban drag is hand-written on Pointer Events, and touch starts on a long press** (owner: "ushlab statusdan statusga o'tkazish imkoniyati yo'qmi"): HTML5 drag-and-drop does not fire on touch at all, and this board is a phone-first screen, so the gesture is built on pointer events — one code path for finger and mouse. Touch requires a ~250 ms hold before the card lifts, which is what keeps a normal swipe scrolling the board and a normal tap opening the card; a mouse skips the wait and starts once the pointer has actually moved 8 px. No drag-and-drop library: the package would be larger than the code it replaced and would still need this touch handling. Three things had to be right and each was found by testing rather than reasoning: an `<a>` is natively draggable and its native drag fires `pointercancel`, killing the gesture (`draggable={false}`); the board must take `touch-action: none` while a card is in the air or the same finger also pans it; and the drop target is resolved with `elementFromPoint`, which returns null outside the viewport — on a 360 px screen only ~76 px of the next column is on screen, so edge auto-scroll is not a nicety but the only way to reach a distant stage. The move is optimistic and reverts if the server refuses.
134. **Integration tests get a 20 s timeout, not the 5 s default**: most of this suite drives a real Postgres — a single case can walk a receipt, a plan, two scans, a departure and a cost recompute, landing at 3–5 s. Under ordinary load that made healthy tests fail on time, twice (m3-planning, then m6-costing), and a timeout that fires on a working test teaches people to re-run instead of to look.
135. **The interface is a design system, not per-screen styling** (owner: "hamma narsa har qayoqda yotgandek tuyiladi"): colours, radii, shadows and type live as CSS variables mapped into Tailwind (`brand`, `ink`, `surface`, `line`), and the shared classes every screen already used — `.card`, `.btn-*`, `.input`, and now `.table`, `.chip`, `.section-title` — carry the redesign, so 67 screens changed appearance without 67 edits. A `PageHeader` / `Section` / `EmptyState` / `Stat` set gives every page the same shape; the diagnosis was that the app had no shared page structure at all, which is what "scattered" actually meant.
136. **One navigation model feeds the home tiles, the sidebar and the phone's tab bar** (`rbac/nav.ts`): a screen is declared once with its icon, its permissions and a tab-bar priority, so it can never appear in one place and be missing from another. On a phone the four highest-priority destinations the actor may see sit in a fixed bottom bar with everything else behind "•••"; from `md` up the same list is a sidebar. Before this, moving between areas meant returning to the home tiles every time.
137. **Icons are hand-drawn SVG, not emoji and not a package**: emoji rendered differently on every Chinese Android phone in the warehouse — different shapes, different weights, sometimes a box — and they were the app's loudest amateur signal. The 35-glyph set in `components/ui/icon.tsx` is smaller than an icon dependency, ships no runtime, and follows one rule (24×24, 1.75 stroke, currentColor) so an icon never shouts over the text beside it.

139. **The brand is the logo's own red, sampled from the file** (owner sent the GSR GROUP lockup): `#B80000` is the mark's dominant colour, and the whole palette is built from it, so the interface and the logo cannot drift apart. A plain `<img>` rather than `next/image`: a 32 px logo gains nothing from the optimiser and would cost an extra request through it.
140. **Dark mode is a cookie and one CSS block** (owner: "ha kerak qorong'i rejim"): every colour already resolved through CSS variables, so the theme is a single `:root[data-theme='dark']` override rather than a `dark:` class on a thousand elements — including the brand tints, which invert (the `bg-brand-50 text-brand-800` icon chip has to become a dark tint with light text) and the semantic colours, which brighten (`green-700` on a dark card is unreadable). Getting there needed a 112-file sweep replacing hardcoded `bg-white` / `text-gray-*` / `bg-blue-*` with tokens — and it caught an e2e assertion written against `border-amber-300`, a styling class that was never a contract; that photo now carries a test id instead.
141. **The tab bar is per role, not per permission** (owner: "skladchilar prixod/yuklash/qabul, sotuvchilar CRM, buxgalterlar pul bilan bog'liq joyni ishlatadi"): one global priority order cannot serve three jobs — the list that puts receiving first for a warehouse operator puts it first for the accountant, who never opens it. `PRIMARY_BY_ROLE` names the four screens each role actually lives in, anything they may not see is skipped so the bar still fills, and a unit test asserts the three cases the owner described. The tab bar also uses SHORT labels (`navShort`): "Управленческий учёт" under a 60 px icon pushed the ••• button off a 360 px screen, while the sidebar and home tiles keep the full name.
142. **A rate is entered the way a person says it: "1 USD = 12 345 UZS"** (owner's round): the FX form asked for `rate_to_usd` — the reciprocal, 0.000081 — which is a number nobody quotes and everybody mistypes. The screen now takes units-per-dollar and `toRateToUsd` inverts it; `perUsd` inverts it back for the list, rounding to a sensible number of places by magnitude (whole so'm, cents for a mid-sized rate, four places for a CNY-style figure). The precision had to move with it: `numeric(18,8)` holds 1/12345 as 0.00008100, which reads back as 12 346 so'm per dollar — an off-by-one in a number the owner typed himself, and real money on a large invoice. Migration 0023 widens all four columns to `numeric(24,12)`. Note the column on `cost_entries` is named `fx_rate_used`, not `rate_to_usd`.
143. **The driver's pairing code is minted with the batch, in the same transaction** (owner: "code shu plan yaratilgani o'zida yaratilib bu sarlavhaga yozib qo'yilsa bo'ladimi"): both batch-creation paths — plan approval and quick batch — call `mintBatchPairCode`, so there is no window in which a trip exists without a code, and the batch header carries it in large type. The loader reads it off the header while the driver is standing at the gate instead of scrolling to a panel and pressing a button. Pairing still burns the code (DECISIONS #118), so the header shows it only while it is unclaimed and the manual "new code" button stays for the second phone or a lost pairing.
144. **The plan editor shows the same figures as the stock table, and switches them to what you are TAKING** (owner: "plan berayotganda kg/m³ ko'rinib tursin, sklad ostatkaga o'xshab"): kg per box, Σ kg, m³ and the colour-coded density now sit on every row, because a plan is built by weight and volume and those numbers were only available in the totals bar at the bottom. Once boxes are ticked the row's Σ figures follow the SELECTION rather than the shelf — on a partial take, the shelf figure answers a question nobody asked.
145. **"Where is my cargo and what do I owe" is one read model, rendered three ways** (`finance/client-cargo.ts`): the owner asked the same question from the client card, the finance ledger and a sales manager's own book, and three separate queries would have drifted apart the first time one of them was fixed. `clientCargo()` returns where the boxes are (grouped by warehouse and by stock/transit/ready, with kg and m³), every trip they travelled on, and the money on each trip; the `CargoSummary` component renders it with a `money` flag so a viewer without finance rights sees the cargo half and not the balances. Trips come from `batch_departed` movements rather than `current_batch_id` (DECISIONS #121) — accepting a box clears the pointer, so a live-pointer query would erase a client's whole history at the moment the cargo arrived.
146. **Debt is attributed to a trip by settling payments oldest-first, not by tagging payments** (owner: "qarz qaysi yukdan kelgan"): a payment carries no batch — a client pays a round number against whatever they owe — so the ledger cannot know which cargo it clears without asking. FIFO settlement is the standard answer and, more importantly, it is the rule the receivables ageing report already uses, so the two screens can never give a client different answers about which invoice is still open. A charge with no batch (a manual correction) is reported separately rather than spread across trips.
147. **Landed cost per client comes from the allocation table, not a re-computation** (owner: "rastamojka summalarini qayerda klientga kiritamiz — narxni shakllantirish uchun"): customs is entered ONCE against the batch and the existing engine already splits every entry down to the box, so `batchLandedCostByClient` is a sum over `cost_allocations` grouped by the box's client. Two figures, because they answer different questions: the total is everything spent on that cargo end to end (China-side receipt costs included) and is what a price has to beat; the batch share is what this trip added. Margin is shown only once a price exists — before that every row would read as a 100 % loss, which is noise, not information.
148. **A client card is not an admin screen** (found by the new e2e): the card lives under `/admin/clients/[id]` for historical reasons, and the admin section's cosmetic gate meant a sales manager clicking a client in their own call list, the dormant list or "my clients" was bounced to the home screen — three CRM features that had never worked for the role they were built for. The gate now also admits `clients.view_own` / `crm.leads`, the card checks its own permission, and the edit form, the deactivate button and the Telegram-cabinet panel are `clients.manage` only. The sub-nav is not rendered at all when a viewer has no admin tabs — an empty strip above every card is worse than none.
149. **The funnel has two shapes, and the phone's is not a kanban** (owner: "mobileda kanban view'ni ishlashga qulay qilib ber"): eight columns side by side on a 360 px screen leaves ~76 px of the next stage visible, so dragging a card to a stage you cannot see is a multi-second edge-scroll that misses as often as it lands — the gesture DECISIONS #133 built works, but the layout it works on does not. On a phone the board is now one stage at a time: a scrollable strip of stage tabs with counts (the funnel at a glance), that stage's cards full width, and a one-tap "→ next stage" button on each card with a bottom sheet behind "⋯" for anything else. The drag board stays from `md` up, where every column fits and dragging is genuinely the fastest move. Both are rendered and toggled with CSS rather than a measured breakpoint: reading the window in JavaScript renders the wrong shape for the first frame, and this is the CRM's home screen. The move logic is shared, so a lost deal asks for its reason whichever shape asked for the move. Consequence for the tests: Playwright gained a `desktop-chromium` project matching `*.desktop.spec.ts`, because a drag test in a 360 px viewport now exercises markup that is `display: none`.
150. **Handover is a warehouse setting, not a permission** (owner: "har sklad uchun «mijozga berish» sozlamasi — faqat TAS/AND'da"): `scan.issue` said who MAY hand cargo over, and every warehouse operator holds it, so the Chinese warehouses got a handover screen no client will ever stand in front of. `warehouses.issues_to_clients` says WHERE it happens; the screen lists only those warehouses and says so plainly when the viewer has none. Migration 0024 seeds the flag from the warehouse type rather than defaulting it to false — customs/distribution warehouses ARE the collection points, and a migration that silently switched handover off everywhere would be a production outage on the morning it shipped.
151. **An expected arrival is a promise, not stock** (owner's item 3): the sales side hears "five boxes to Yiwu on Friday" days before those boxes exist anywhere in this system, and until now that sentence lived in a chat while the warehouse found out when a courier walked in. `expected_arrivals` holds no boxes, no letters and no money — it is a row a warehouse reads in the morning. It closes ITSELF when the real receipt is confirmed, inside the receipt's own transaction, but only on an unambiguous match (exactly one waiting row for that client at that warehouse): with two open promises there is no way to know which receipt answers which, and guessing would close one that is still genuinely outstanding. The close can never fail a receipt — a planning aid that can block goods coming in is worse than no planning aid.
152. **`boxes.id IN (SELECT …)` as a JOIN condition is a table scan per row** (found by the new arrivals test, which took 28.7 s): the incoming-trucks query joined boxes to batches through a correlated subquery over `box_movements`, so Postgres walked the whole box table once per batch — a cost that grows with every receipt the company has ever taken. Joining `box_movements` directly and then `boxes` on its `box_id` uses the indexes and returns the same rows in 0.36 s. The general rule for this codebase: batch membership is a JOIN through `box_movements`, never a subquery in a join predicate.
153. **"Trucks" is a fleet view, not a settings screen** (owner: "/trucks o'rniga «qaysi partiya qayerga yetib bordi»"): the truck PRESETS — names and capacities — are opened twice a year and now live at `/admin/trucks` with the rest of the settings. `/trucks` answers what a logist actually opens a page called trucks for: which batch is loading, which is on the road, which has landed and where each one physically is — the arrival if it has one, otherwise the newest GPS fix from the driver's phone, otherwise the logist's manual pin, and it says which of the three it is showing.
154. **A test that walks away from a debt breaks the next run** (found on the second full e2e pass): m9 priced a client and left the charge unpaid, which armed the handover debt gate and made m5-issue fail — on a suite that shares one database in file order, leftover state IS the next test's input. m9 now settles its own charge before finishing. Related: file names carry the ordering, and lexicographic sorting puts `m10-…` between `m1-…` and `m2-…`, so a spec that needs a departed truck cannot be called m10; the arrivals spec is `m9b-arrivals.spec.ts`.
155. **The dashboard reports off the ledger, never a second opinion on the P&L** (owner: "butun tizim holati — logistikadan moliyagacha"): the money block shows charged, received and owed — figures that come straight out of `client_transactions` — and links to the P&L for anything derived. A tile computing revenue its own way would eventually disagree with the report by a rounding rule or a period boundary, and a dashboard that contradicts the accounts is worse than a dashboard without money on it. Each block is a separate query behind its own permission, so an operator's page never computes an accountant's totals just to throw them away, and a viewer without finance rights sees the block ABSENT rather than empty — an empty money card reads as "we earned nothing".
156. **A Date interpolated into a raw `sql` fragment reaches postgres.js untyped and it refuses to send it** (`ERR_INVALID_ARG_TYPE: Received an instance of Date`, which surfaced as a 500 on the new dashboard): drizzle's comparison helpers (`gte(col, date)`) know the column's type and encode the value, but inside `sql\`… filter (where x >= ${date})\`` there is no column to learn from. Bind an ISO string with an explicit `::timestamptz` instead. The general rule: raw SQL fragments take primitives, and any date in one is a string plus a cast.
157. **The corridor projection scales longitude by cos(reference latitude)** (owner: "xarita to'g'ri nisbatlarda bo'lsin"): the old fallback drawing used 16.6 for longitude against 24 for latitude — a ratio of 0.69 where the honest figure at 35°N is 0.819 — so the whole corridor was squeezed sideways by about 16 % and distances on the drawing were not comparable to each other. The viewBox is now the exact projected extent, unrounded, because rounding clipped the outermost graticule lines. The hand-drawn "country hint" blobs are gone: they were never real geography and they were drawn against the old projection, so fixing the proportions made them wrong. A generated lat/lon grid replaced them — it IS the projection, so it cannot disagree with the marks placed on it.
158. **Shape tells a warehouse from a truck, not colour and not emoji** (owner: "sklad va mashina belgilari aralashmaydi"): a warehouse is a blue rounded SQUARE with a roof, a truck an amber CIRCLE with a box on wheels — different silhouettes, so they stay distinguishable when they overlap, when the map is zoomed out, and for anyone who cannot separate the two hues. 🏭 and 🚛 were two similar blobs that rendered differently on every Chinese Android in the warehouses (DECISIONS #137). The labels are offset in opposite directions — truck code above the mark, warehouse code below — so a truck standing at its destination does not print over the warehouse's name, and a legend in the corner says which is which.
159. **Leaflet has to be told when its container changed size**: the fullscreen toggle grows the element from CSS, which Leaflet never sees, so it keeps drawing tiles for the old box and leaves grey bands where the old edge was. `invalidateSize()` plus a re-fit runs on every fullscreen change, after a short delay so the CSS transition has landed. Fullscreen itself is a `fixed inset-0` layer rather than the Fullscreen API: the API needs a user gesture, is refused inside some in-app browsers, and would take the app's own header and tab bar with it.
160. **The scanner decodes the guide square, not the whole frame** (owner: "ekranda ko'rinadigandan kattaroq joyni scan qilyapti"): the preview used `object-cover`, which crops what the operator SEES but not what the decoder reads — so a label lying beside the box, or still in the previous one, was picked up off screen and accepted with no way to tell where it came from. Every frame is now drawn into a canvas cropped to the guide before it reaches either decoder, which also forced the zxing fallback off `decodeFromVideoElement` (it reads the whole frame and cannot be told otherwise) onto the same cropped canvas on the same interval. The dimmed surround is four positioned panels rather than a masked overlay: `mask-composite` is still unreliable in the Android WebViews these phones run. A drawn frame that does not match what is read is worse than no frame — it teaches the operator to trust an aim that does not exist.
161. **A picker must not offer what the action will refuse** (owner: "faqat o'zinikini belgilasin"): the quick-batch form listed every warehouse as an origin while `createQuickBatchAction` scoped the authorization to the actor's own — so a warehouse manager could pick a neighbour's warehouse and get an error that looked like a bug rather than a rule. The origin list is now the actor's warehouses, and collapses to a plain label when there is only one; the destination stays the full list, because sending cargo elsewhere is what a batch IS. The plan editor had the same asymmetry inverted — it scoped BOTH ends, leaving a scoped planner unable to name any destination — and is fixed the same way: origin scoped, destination open.
162. **A truck is filled by weight and volume, so the loading screen counts them** (owner: "yuklash paytida umumiy kubi, kilosi va kg/m³ ko'rinsa"): the loading snapshot API now carries each box's kg and m³ (the lot's totals divided by its box count — nothing here weighs a box on its own), and the screen totals what has actually been scanned aboard, density included. The box counter alone could not answer "will the rest fit", which is the question being asked at the door of the truck.
163. **A locale test that compares bundles to each other cannot catch a key missing from all of them** (`/admin/settings` threw on every visit for weeks): `crm_dormant_days` was added to `SETTING_DEFAULTS` and to none of the four bundles, so the parity test saw four bundles in perfect agreement while the screen — which renders `t('descriptions.<key>')` for every key — died at render. The new test asserts the SOURCE OF TRUTH against the bundles: every key in `SETTING_DEFAULTS` must have a description in every locale. The general lesson for this codebase: parity tests need an anchor outside the things being compared.
164. **A pre-rendered notification body is the message, checked before the switch** (found by the same audit): `renderTelegramText` had a case for `DailyDigest` and none for `CrmFollowUps` or `CrmDormant`, so both CRM digests fell through to `default` and every reader received the literal string `CrmFollowUps` and a link to `/receipts/undefined`. Adding two cases would have left the next digest broken the same way. A digest is composed per recipient from rows no case here can reproduce, so `payload.text` is now honoured for any type — and the default branch links to a receipt only when there IS one. Verified by reverting the fix and watching the test fail.
165. **One undeliverable Telegram message must not hold the queue** — `sendPendingTelegram` rethrew on the first failure so pg-boss would retry, which aborted the remaining rows in the batch; a single driver who blocked the bot stopped every message behind them, including `MissingInTransit`. Each row is now attempted, its own error recorded against an attempts counter (migration 0025), and the batch throws once at the end so pg-boss still retries — rows already `sent` are excluded from the next pass, so a retry re-sends nothing. At six attempts a row goes terminal: a blocked bot never becomes deliverable, and a row that retries for ever keeps the whole job red.
166. **Scope intersects across roles; permissions union** — `warehouseScoped` was `roleCodes.every(isScoped)`, so a second role removed warehouse scoping altogether and handed one warehouse's operator every warehouse in the company. It never fired only because no user held two roles. The predicate is now `isWarehouseScoped()` in `catalog.ts`, exported so the rule has one home and the TEST CALLS THE REAL FUNCTION — a test that restated the predicate would have passed just as happily after a revert.
167. **`getActor` is memoised per request with React `cache`**: it is called from 70-odd files and each call was three round-trips, so a single dashboard render repeated the same three queries a dozen times. `cache` keys on the arguments (there are none) and is discarded with the request, so two users cannot see each other's actor. This is load-bearing for anything record- or field-scoped, where the actor is consulted per row rather than per page.
168. **Grants are rows an admin edits, not a matrix in TypeScript** (owner: "hech qanday biznes-obyekt hard-coded bo'lmasin", starting with roles): `ROLE_MATRIX` reached the database once, through an insert-only seed, so adding a permission to a role needed a deploy and removing one was impossible — the answer to "who may do what" was the one piece of company policy the company could not change. `/admin/roles` writes `role_permissions` directly; the matrix stays as the SEED for a fresh install and as the definition of the nine shipped roles. `PERMISSION_CODES` remains in code on purpose: a permission is a name the code checks, so inventing one in a form would produce a checkbox that governs nothing.
169. **The guardrails are the feature; the checkboxes are the easy part.** A permissions screen that can lock the owner out, or let a manager quietly promote himself, is worse than no screen — so `setRoleGrants` refuses three things. (a) A role the EDITOR HOLDS: this is how someone locks themselves out and how someone grants themselves the accounts, and it is refused in the service, not only greyed out in the UI. (b) A permission the editor does not hold — without this, anyone with `platform.roles.manage` is effectively a super admin, since they would tick every box on a role and assign it to themselves. Only the DIFFERENCE has to be grantable, or an editor lacking one permission a role already has could never touch that role at all and would delete and recreate it instead. (c) A write that leaves NO active person able to manage roles — checked inside the transaction against the state the write is about to create, so it sees the result rather than the past, and rolls the whole thing back.
170. **A role an admin has edited is left alone by the seed** (`roles.grants_customised`): the seed runs on every deploy, so without a flag my next release would silently undo the owner's configuration — the one behaviour that would teach him never to touch the screen. A role edited in the UI is marked, the seed skips it and PRINTS which roles it skipped, so a missing new permission after an upgrade has a visible cause. A newly invented role is marked customised at birth: it protects nothing yet, but it stops the seed ever adopting a code that later ships.
171. **A disabled checkbox posts nothing, which on a replace-all form means DELETE.** The grants form submits the whole set at once (an empty submission is a real "no permissions" answer, not a missing field), so a permission rendered disabled — because it is the editor's own role, or one they cannot grant — would be stripped on save by a UI detail nobody could see. Those codes are re-posted as hidden inputs. The general rule for this codebase: a form that replaces a set must post the whole set, locked members included.
172. **A role nobody can be given is not a role** (caught while wiring the screen up): the user form still rendered `ROLE_CODES` from the catalogue, so the role constructor built roles that could not be assigned to anyone. The form now reads the roles TABLE. Two consequences: the action's zod schema can no longer be `z.enum(ROLE_CODES)`, so codes are resolved against the table BEFORE the person is written and the save is refused if any code fails to resolve — `inArray` would otherwise drop the unknown ones in silence and report success; and labels fall back to the role's own name, because only the nine shipped codes have a translation and next-intl throws at RENDER time on a missing key.
173. **A test that clicks save and immediately reloads is measuring the past** (the roles e2e failed once, on a write that had in fact happened): the reload raced the server action's transaction, so the fresh render read the pre-commit state and the assertion reported a lost grant that was sitting in the database a moment later. The spec waits for the action's own success marker before navigating. The spec also invents and then deletes its own role rather than editing a shipped one — this suite runs one worker over one database in file order, and stripping a permission off `warehouse_operator` here would break receiving three files earlier on the next run (DECISIONS #154).
174. **Which objects may carry a custom field is a TABLE, not a CHECK constraint** (owner: "hech qanday biznes-obyekt hard-coded bo'lmasin"): the restriction to leads and clients was encoded in five places that had to be edited in lockstep — a SQL CHECK, a drizzle `check()`, a zod enum, a TypeScript union on five signatures and two hard-coded `<option>`s. `custom_entities` replaces all of it with rows the value tables reference by foreign key, so widening is an INSERT. The registry in `platform/fields/registry.ts` is still code, and honestly so: it carries what a row cannot — the translation key, the permissions that may WRITE that object's fields, and whether the object can be a lookup target. Custom entities the owner invents (a later phase) are rows in that table with a generic card; the registry lists the objects whose SHIPPED cards render the panel.
175. **Answers live in typed columns, not one jsonb blob** (migration 0027): the owner asked to filter and sort by these fields, and out of a jsonb value "5" sorts after "40" — a wrong answer rather than a cosmetic one — while a range filter cannot use an index at all. `value_text / value_num / value_date / value_bool / value_list / value_ref / value_ccy` with a CHECK that exactly one is set, and a btree on `(field_id, value_*)` per type. Money is the one type with two columns, because an amount without its currency is not an answer and a default currency would silently price things in dollars. The backfill from the old `value` column ran against a clone of the live database — 76 real answers across three types, none lost — and drizzle wraps every pending migration in ONE transaction, so a failure anywhere leaves the database exactly as it was.
176. **Filtering is SQL, sorting is memory, and that split is deliberate**: every list in this app is capped with `.limit(N)` and none of them paginate, so filtering after the cap would search the first 200 clients rather than all of them, while sorting after it orders exactly the rows on screen. Filters compose as one `EXISTS` per predicate — a JOIN would multiply rows when a record answers several fields, and a subquery in a join predicate is the table scan DECISIONS #152 was written about. Sorting reuses the existing `sortRows` with a longer allow-list; a custom column is just another key, and it sorts correctly because the value arrives from a numeric column.
177. **No generic query builder** (this is what killed one of the three designs I weighed): a `listWithCustom(entity, filters, sort)` over a registry has to reproduce 17 tables' worth of warehouse scoping, soft-delete predicates and built-in columns from strings, in the platform layer, which is forbidden from importing wms at all. `fields/filter.ts` instead returns SQL FRAGMENTS a screen drops into the query it already has, plus a decorator that hangs answers onto rows already fetched. Wiring a second list screen is six lines and no new abstraction.
178. **Hidden is not cleared.** A conditional field whose predicate turns false is simply not rendered, so it is absent from the next payload, and `setFieldValues` only touches fields PRESENT in the payload — the stored answer survives. The alternative, deleting the value of any field whose predicate is false, destroys data across the whole table the moment a parent dropdown is edited or merely deactivated, silently, as staff save unrelated changes. For the same reason `deleteField` refuses while another field's `show_if` points at it: a predicate aimed at nothing evaluates to hidden, so deleting one dropdown would make a set of unrelated fields vanish from every card. Chained conditions (A→B→C) are refused rather than resolved — a dependency graph's first cycle would hang the render.
179. **The field editor reuses `admin.dictionaries.manage` instead of minting a permission code.** A new code reaches an existing role only through the seed, and since DECISIONS #170 the seed SKIPS any role an admin has edited — so on a database where the owner had customised `super_admin`, a fresh code would sit in the catalogue granted to nobody, with `setRoleGrants` refusing to grant a code the editor does not hold. Unreachable screen, no way back through the UI. `admin.dictionaries.manage` shipped in the original matrix, is held by `super_admin` and `admin` on every existing database, and had no screen behind it until now; defining fields IS reference-data work.
180. **A file-typed field uploads into its own attachment group.** The group id is a uuid minted per (file field, record), stored in that answer's `value_ref`, and used as the attachment's `entity_id` under a new `custom_field` entity type. Reusing the record's own identity would have put the document into the receipt's general attachment panel, where anyone holding `receipts.edit` could delete it without ever seeing the field it belonged to. The group is minted when the card RENDERS, so files can be attached before the first save; an abandoned form leaves an orphan group and nothing else.
181. **A custom payload is validated before the record it belongs to is written** — the parent write and the answers are not one transaction, so `createLead` used to commit and only then reject a value, leaving a saved lead behind an error message that read as if nothing had been created. Adding per-field rules made that far more likely. `validateValues` runs the same coercion with nothing to write, and the create actions call it first.
182. **Two editors writing one table is how one of them goes stale**: the field section is gone from `/crm/settings` (a link remains) rather than left in place during a transition. Related, the client card's custom fields no longer sit behind `crm.leads` — a client manager without CRM rights could not see fields on the card they own. The write permission is a LIST per object in the registry (`clients.manage` OR `crm.leads` for a client), because narrowing it to one code would have taken the screen away from the sales managers filling it in today.
183. **CI runs vitest and Playwright against ONE database, so an integration test that leaks DEFINITIONS breaks unrelated specs** (found by CI, not locally — I had re-seeded between the two runs, which the pipeline does not). `fields.integration.test.ts` deleted its answers and left its 25 field definitions behind; two of them were enough to fail the suite. An always-visible REQUIRED field made every save on the client card fail, and a `lookup` field pointing at clients rendered every client's `code · name` into an `<option>` on the client card, which turned `m0-smoke`'s unscoped `getByText(name)` into a strict-mode violation. The cleanup now deletes the definitions themselves (straight from the table — `deleteField` refuses while a dependent exists; answers follow by cascade). The lesson generalises beyond this file: state that only CONFIGURES the app is more dangerous to leak than state that merely sits in it, because it changes what every other screen renders. The related e2e fragility was fixed too rather than papered over — `m0-smoke` now asserts the HEADING, because a client-lookup field is a configuration the owner may legitimately create in production and no spec should break when he does.
184. **A task is not the CRM follow-up, and the follow-up was not rewritten into one** (owner: "tasklar calendarlar", and separately "sistemani ishlab turgan joylarini buzib qo'yma"): a follow-up is a reminder a sales manager sets for THEMSELVES on a lead, and it has worked since the CRM shipped; a task is work one person gives another, with an assignee who is not the author and a closing result. Merging them would have produced one tidy list at the cost of a screen the sales side uses daily. `/bugun` renders both, labelled, and `/crm/today` answers exactly as before. The two mechanisms may converge later — after the task engine has proved itself, not before.
185. **A deadline of "Friday" is the END of Friday.** `parseDue` stores a bare date at 23:59:59.999, because the alternative puts the whole company's list into the red at one minute past midnight on the day the work is actually due — and a screen that cries wolf every morning is one nobody reads by the second week. The same boundary is why `calendarTasks` widens its window to whole days: an all-day task on the last day of the month sits after the caller's own clock and vanished from the month it belonged to (found by the test, not by review).
186. **Tasks reuse the entity registry rather than inventing their own list of what can carry one.** `tasks.entity_type` is a foreign key into `custom_entities` (migration 0027), so a task hangs off a client, a receipt, a batch or a plan today, and off the owner's own entities the day those arrive — with no second registry to keep in step. Both pointer columns are null for a standalone task, and a CHECK forbids half a pointer, because half of one renders as a dead link. Where each record LIVES is a separate map in `tasks/view.ts`: the registry says what a client is, the routes say where its card is, and a type with no route simply renders without a link instead of a broken one.
187. **Cancel, never delete.** A task somebody was given and then told to drop is evidence about how the work went. `cancelTasksFor` sweeps a record's OPEN tasks when the record itself goes and leaves the closed ones alone — a finished job is history, not something to tidy away.
188. **The task digest is its own mute group.** Folding `TasksDue` into `digest` would mean that muting the warehouse summary also silences the one message telling a person what they personally owe today. Someone switching off "nothing is on fire" reports is not asking to stop hearing about their own work, so `tasks` is a fourth group with its own checkbox. The digest is silent when a person has nothing due, and is sent per recipient — a list of somebody else's work is a message people learn to swipe away.
189. **No permission code for tasks.** Everyone has work assigned to them, so being logged in is the gate for raising one and for closing one you were given; seeing OTHER people's months reuses `crm.leads.view_all` / `reports.all_warehouses`. This is a company of twenty where the warehouse manager asks the VED manager for a calculation several times a week, and a permission matrix over that is bureaucracy nobody would maintain — quite apart from the lockout trap a new code walks into (DECISIONS #179).
190. **The tab bar gained /bugun by role, not by priority number.** Adding a `primary` to the nav entry would have collided with the numbers already in use and ordered the bar arbitrarily; `PRIMARY_BY_ROLE` (DECISIONS #141) names it explicitly for the office roles and leaves the warehouse bars untouched, because receiving IS the job there and tasks are occasional. `/crm/today` left the sales bar in the same move — `/bugun` shows those follow-ups, and two doors to one list is worse than one.
191. **A recurring task spawns its successor on CLOSE, never ahead of time** (owner: "ha" to recurring tasks): a materialising scheduler would leave four unfinished copies of "check the till every Monday" on somebody's screen after a month away, and a list that is mostly stale is a list people stop reading. One rule, one open instance. The corollary is that CANCELLING is how a series ends — completing carries it on — which needs no extra control and says what it means. The next date is computed from the DUE date rather than from now (a Monday task finished on Saturday lands on the following Monday), rolled forward until it is in the future (closing a month of missed Mondays must not create another missed Monday), and month steps clamp to the end of a short month, because JavaScript's own overflow turns "the 31st of every month" into a rule that silently skips February.
192. **Trucks on the calendar are DERIVED, not stored** (owner: "ha yaxshi bo'lar edi"): departures and arrivals are read from `batches.departed_at` / `arrived_at` and promised cargo from `expected_arrivals`, so the calendar cannot drift from the truck board and a date corrected on a batch card is corrected everywhere in the same moment. A second copy would have been a second thing to keep true. It is a toggle carried in the URL because a sales manager wants their own work and nothing else, and the calendar PAGE merges the wms feed with the platform-level tasks — neither module learns about the other.
193. **The person who assigned the work is the manager this system has** (owner: "ikkalasiga habar ketsin"): overdue work notifies the assignee AND the author, because there is no reporting hierarchy here and inventing one for a single message would mean maintaining a second org chart beside the real one. Someone who gave you a job is by definition waiting on it. Self-assigned tasks are not sent twice — the same list arriving in two messages is how a channel stops being read.
194. **What a person MAY open and what is any use to them are two different questions** (owner: "mening kunim / kalendarlar skladchiga korinishi shart emas … juda kop funksiyalar bolib ketti"). `canSee` answers the first from the permission matrix; `MENU_BY_ROLE` in `nav.ts` answers the second, per job. They are separate functions on purpose and composed as `canSee && isRelevant`, in that order — relevance can only ever REMOVE an entry, never add one, so it cannot quietly become a second and sloppier permission system. A unit test asserts exactly that over every shipped role, because the argument only holds while the composition does. Measured effect: warehouse operator 15 menu entries → 8, warehouse manager 15 → 11, sales manager 14 → 9, VED manager 11 → 8, accountant 13 → 10, viewer 10 → 5, logist 22 → 13.
195. **The menu's default was "show everyone", and eight entries were living on it.** `canSee` returns true when an item declares no `permissions`, which is right for `/` and was never reviewed for the seven that followed it — so a warehouse packer's home screen offered the calendar, the funnel and the truck board. Auditing this needed a script that enumerated every role against every entry rather than a reading of the file: the entries that were WRONG were exactly the ones with nothing written on them, which is what makes them invisible to review.
196. **An uncurated role gets the WHOLE menu, deliberately.** Relevance is not security, so its failure direction must be "too much menu", never "an empty app": `isRelevant` returns true for a role with no curated list, and — the case that matters — for a viewer holding ANY uncurated role alongside curated ones, so the owner logging in with a second role keeps his own menu. This is what makes `/admin/roles` (DECISIONS #168) still work: a role the owner invents tomorrow is born with a full menu and is narrowed only if it is worth narrowing.
197. **Hiding a screen must never be able to hide the work.** `/bugun` left the warehouse menu, so a task assigned to a packer would have existed with nothing on their screen pointing at it. The home page now carries a banner with the count when anything is due or late, on the one screen everybody opens; the route itself is untouched and still answers. Menu decisions and delivery are decoupled — the e2e asserts both halves in one file so they cannot drift apart, since a change that satisfies only the first is not tidying, it is losing work.
198. **Five admin pages had no authorization at all, and two checked the wrong code.** `/admin/users`, `/admin/users/new`, `/admin/users/[id]`, `/admin/warehouses/new`, `/admin/warehouses/[id]`, `/admin/clients/new` and `/admin/settings` sat behind the `(protected)/admin` layout gate — which admits anyone holding `clients.view_own` or `crm.leads`, i.e. every sales manager — and the two that did check used `admin.warehouses.manage` for the user list and the settings screen. A sales manager who typed `/admin/users/new` got a working form that creates logins and assigns roles. Every page now states its own permission; the layout gate is what decides whether the SECTION appears, and cannot be what decides whether a page is safe.
199. **`scoped && ids.length ? inArray(...) : undefined` — the `: undefined` was the bug, in thirteen places.** A warehouse-scoped person with no warehouse assigned (a new hire, or someone whose assignment was pulled) produced no WHERE clause at all and read every warehouse in the company. Silent, and in the permissive direction. `rbac/scope.ts` replaces the ternary with a helper that CANNOT express "no filter" for a scoped user: unscoped → no filter, scoped with warehouses → those, scoped with none → `sql\`false\``. The shape of the fix is the point — the old expression stayed wrong for two years because writing it correctly and writing it wrongly look identical at the call site.
200. **The lists were warehouse-scoped and the CARDS were not.** `/receipts` never showed a Guangzhou receipt to a Yiwu operator, and `/receipts/<uuid>` always did — and a uuid travels by Telegram link every day here. `inScope()` now guards the receipt, crate, plan, batch and box cards, with `notFound()` rather than a message, because "this exists and is not yours" is itself information. A batch is in scope at EITHER end: it belongs to its origin until it arrives at its destination and both warehouses have a real reason to open it. A box is in scope at its current warehouse or at the one that received it, so a transferred box stays readable to the people who packed it.
201. **A task id was enough to close anybody's task.** The mutations checked that you were logged in and nothing else, so any employee could complete, cancel, reassign or rewrite any task in the company — and the audit trail would record it as deliberate. `canActOnTask` allows the assignee, the author, and holders of `crm.leads.view_all` / `reports.all_warehouses`: the same pair `/kalendar` already uses for "may look at everyone's month", so there is one rule rather than two that drift. CREATION stays open (DECISIONS #189) — the objection was never that people ask each other for things. This required `TaskContext = AuditContext & { actor }`, because the audit context carried an id and the question needs permissions.
202. **A read-only viewer had a two-icon tab bar** (found while checking that relevance had not shrunk anybody's bar — it had not, this was already broken). Only `/` and `/stock` carry a `primary` number among the ten screens a viewer may open, and the generic fallback can only choose from numbered entries, so half the phone's bottom bar was empty. `PRIMARY_BY_ROLE` now names the viewer's four. The general lesson is that a fallback ordering over an optional field silently degrades for whoever the numbers were not chosen for.
203. **A deal holds the quote and the reality side by side, and the reality side is never typed in** (docs/DEALS.md, settled with the owner). The pain he described is not a missing record — Telegram and Excel already hold one — it is the gap between the price a client was quoted and the cargo that turned up, seen too late: quoted 1 m³ for 200 USD, the cargo arrives at 1.4 m³, and either a sales manager happens to notice or there is an argument in Tashkent. So `deals` carries the quoted volume, weight and amount, and the actual side is SUMMED from the receipts that point at the deal (`receipts.deal_id`, nullable for ever). Giving anyone a box to type the actual figures into would make the comparison meaningless the first time somebody "corrected" it.
204. **The alert fires on cargo that is BIGGER than quoted, and says nothing about cargo that is merely not all here yet.** Comparing on "outside the threshold" alone was the obvious implementation and it was wrong: a shipment split over two days — the owner's own example, and a normal week here — reads as 50 % UNDER on the first receipt, so every split job would have produced a false alarm, and a channel that cries wolf weekly stops being read by the second month. `worthAlerting()` is the extra predicate; the under-delivery half is still computed and still shown on the deal card, where somebody is already looking, and simply never pushed. Found by the integration test, not by review.
205. **Price control runs inside the confirm transaction and cannot fail it.** The alert is worth something only while the cargo is still in the Chinese warehouse — the one moment the client can still say "then send it back" — so it is emitted from `confirmReceipt` rather than from a screen somebody might not open. It is wrapped in a bare `catch` for the same reason `closeExpectedOnReceipt` is: the boxes are physically in the building, and a receipt must never fail to be recorded because an advisory message could not be composed. It never blocks anything either (owner's answer 1: "notify above 10 %, never block loading").
206. **The comparison is against the WHOLE job, not the receipt that triggered it.** Reality is re-summed across every non-voided receipt of the deal each time one lands, so the second half of a split shipment brings the job back inside the threshold instead of firing again. A voided receipt drops out of the sum entirely — counting a cancelled receipt's volume would report a job 40 % over when it is not.
207. **Deferred payment belongs to the DEAL and carries an end.** "I'll pay when it's all here" on a CLIENT becomes permanent, everybody forgets it, and that is how a debt gate quietly dies; on the deal it is scoped to the job it was agreed for. It carries a reason, an author and one of two end conditions, and a CHECK constraint refuses a deferral that has neither. The natural condition self-resolves — the system already knows how many boxes belong to the job — and a LOST box is excluded from "still outstanding" rather than counted, because a box that is never arriving would otherwise hold the deferral open for ever. `activeDeferrals` stops honouring an expired one immediately, before the hourly sweep has run, so a debtor is not invisible until the next job tick.
208. **No new permission code for deals.** Both sides of the business work one — the sales manager who quoted it and the VED manager who recalculated it (owner's answer 2) — so the gate is the LIST `crm.leads | ved.docs | clients.manage`, the same shape the fields registry uses (#182). A fresh code would reach existing roles only through the seed, and since #170 the seed SKIPS any role an admin has edited, which on the owner's own database means an ungrantable screen with no way back through the UI (#179). The deferral is the exception and reuses `finance.debt_override`, which already means exactly "who may let a debt slide".
209. **The kanban board was extracted rather than copied.** The deal board and the lead board differ only in what a card SAYS; four hundred lines of pointer handling, hold-to-drag, edge-scrolling and the phone's stage strip would have become two copies that diverge at the first bug fix. `components/kanban.tsx` is generic over the card and takes its labels as already-translated STRINGS — a client component cannot resolve a namespace its caller chose, and a missing next-intl key throws at render time in every locale. The lead board's e2e (drag on desktop, one-tap move on the phone) is what proves the extraction did not break it.
210. **A deal starts from a client, never from a stranger.** Somebody with no code yet is a LEAD; winning that lead creates the client, and only then a deal. Keeping the two apart is what stops the deal board turning back into the funnel it sits beside — a funnel filled with the same 1442 clients shipping again and again stops being a funnel (docs/DEALS.md, "The board"). `linkReceipt` refuses across clients outright: a receipt filed under another client's deal makes two clients' money wrong and is invisible afterwards.
211. **The mute-coverage test now reads the routing instead of a copy of it.** It listed the event types by hand under a "keep in sync with service.ts" comment — a promise no test can keep, and the three price-control types were added and went straight through it while being unmutable. It now extracts every `case 'X':` from inside `buildRecipients` and asserts each one is in a mute group. Shown to fail by removing the new types from the group. The general rule this codebase keeps relearning: compare against the source of truth, never against a second copy of the same list (#163, #166).
212. **A deferral the handover gate cannot see is a note, not a feature.** The deferral shipped able to record a decision — reason, author, end condition — while `issueBoxes` went on reading the raw balance, so the warehouse still refused the client's cargo, the operator still pressed the one-click override, and the reason went straight back to being a Telegram message. Found by the audit, not by the tests: every test asserted on the deferral's own state and none asked whether anything downstream behaved differently. The gate now subtracts `deferredBalanceUsd`, and the integration test asserts the SUBTRACTION rather than the flag.
213. **A charge has to carry its job before a deferral can cover it** (migration 0031, `client_transactions.deal_id`). Charges are raised from batch pricing and point at a batch; a deal points at receipts; the two do not meet, so "the money for THIS job waits" had nothing to compute against. The column is nullable for ever and that null is a correct answer, not a gap: a charge posted from batch pricing is not covered by any deal's deferral, which is exactly right — the deferral was granted for one job, and an unrelated older debt must still block. That is asserted directly ("does not let a deferral on one job excuse an unrelated old debt").
214. **The client's balance is never rewritten by a deferral — only the figure the GATE decides on.** A screen that quietly netted the deferred part off the displayed debt would be lying about what is owed, and the sales manager phoning that client needs the true number. So `/issue` shows the full debt, colours it amber rather than red when nothing blocking remains, and states the deferred amount and its reason: an open gate beside a real debt reads as a bug unless the screen says why.
215. **Posting the charge lives on the DEAL card, gated on `finance.manage`.** Agreeing what a job costs and putting money on a client's account are different powers — the deal-write list (`crm.leads | ved.docs | clients.manage`) covers the first and must not confer the second. The amount is pre-filled with the RE-PRICED figure when the cargo came out over the threshold and with the original quote otherwise, because that is the number the person is about to type either way; and the card shows what has already been posted, since being billed twice for one shipment by two people on two afternoons is the commonest way a client ends up disputing an invoice.
216. **A dropdown that cannot render the stored value is a dropdown that DELETES it.** `salesManagerOptions` was `roles.code = 'sales_manager'`, the client form is a bare `<select>` whose first option is blank, and the two together silently reassigned every client whose owner was the owner himself, the logist, or anyone on an invented role — the browser picked the blank option and the next save, for a phone typo, wrote NULL. Measured on the real imported data: 269 assigned clients, **two owners** the old list could not render. The list is now built from a PERMISSION (`crm.leads | clients.manage`) rather than a role name, active users only, plus an `include` argument that re-adds whoever is currently assigned even if they no longer qualify. This is DECISIONS #171 restated in its general form, which is what it should have been the first time: **a form that replaces a value must be able to display every value it might replace.** The lead card had the identical bug and is fixed the same way.
217. **The client book asked for the WAREHOUSE admin permission.** The menu entry, the create page and all three mutations gate on `clients.manage`; the list page and its XLSX route gated on `admin.warehouses.manage`. The logist holds the first and not the second, so he could create a client, edit the card and mint a Telegram cabinet link — and the «Mijozlar» entry in his own menu bounced him home. Any role invented on `/admin/roles` inherits the same dead entry. All three now agree, the admin layout admits `clients.manage`, and the e2e opens the page AS the logist rather than asserting a permission string.
218. **Menu curation is a claim about a job, and it can be wrong.** `MENU_BY_ROLE` (#194) left `/admin/clients` out of the logist's list — a curation mistake, not a permission one, and invisible to every test that checked permissions. The e2e that opens the book as the logist caught it. The lesson for the curated lists: assert them by DRIVING the role, never by reading the array.
219. **A client is findable by the number that is ringing.** Every staff lookup matched code and name only, while the Telegram cabinet had matched phones correctly since Phase 2.2 — so a manager holding a client's number could not find the card, in the one moment they needed it. `phoneNeedle` reduces a query to its last nine digits (the cabinet's rule, #111) and the search compares against the same reduction of each stored phone, so a number typed with a country code finds a card stored without one and the other way round. Five digits is the floor: below it the phone branch is skipped entirely, or a search for the real client marking `444` runs a phone sweep that buries the code hit it was meant to help.
220. **A cap that does not say it is a cap is a screen lying about the size of the business.** The client book printed the number of rows it had fetched as if it were the total, so the owner's screen told him he had 200 clients. It now runs a `count(*)` with the same WHERE and renders "N of M" plus a "narrow the search" hint, and the row cap is shared with the XLSX route so the file and the page cannot disagree about what "the list" means. The same shape exists on stock, the ledger and the funnel — those are the next ones.
